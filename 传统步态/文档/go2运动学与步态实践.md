# Go2 运动学与步态实践（顺序.md 第 1 阶段）

对应 `doc/顺序.md` 第 1 阶段目标：**能自己写一个三连杆腿的 FK、Jacobian、IK**。

不用 RL，从关节角一路打通到 MuJoCo 里走起来，把 `cmd_vel → τ` 这条链亲手连一遍。

## 代码

| 文件 | 内容 |
|---|---|
| `tools/learn/leg_kinematics.py` | 单腿 FK / Jacobian / IK，纯 numpy，带自检 |
| `tools/learn/go2_walk.py` | trot 步态 + PD + 重力前馈 + 键盘遥控 |
| `tools/learn/terrain.py` | 六种地形（box 拼装 / heightfield） |

环境：`./third_party/mjlab/.venv/bin/python`（mujoco 3.8.1，主 `.venv` 里没装）
模型：`~/mujoco_menagerie/unitree_go2/scene.xml`，执行器是 **torque motor**，PD 必须自己写。

```bash
# 自检
python tools/learn/leg_kinematics.py

# 开窗遥控（W/S 前后  A/D 转向  Q/E 平移  空格停）
python tools/learn/go2_walk.py -T 600 --terrain rough

# 无窗测达成率
python tools/learn/go2_walk.py --headless -T 12 --vx 0.4 --terrain stairs
```

## 一、运动学

几何参数取自 `go2.xml`：abduction 偏置 `d=0.0955`，大腿 `l1=0.213`，小腿 `l2=0.213`。

```
关节角 q ──FK──> 足端位置 x
   q̇   ──J──>  足端速度 ẋ = J q̇
   τ   <──Jᵀ── 足端力 F     τ = JᵀF
```

自检结果：

| 项 | 误差 |
|---|---|
| 解析 Jacobian vs 数值 Jacobian | 7e-11 |
| IK 往返 `q→x→q` | 7e-16 |

### 坑 1：IK 有两个分支，光靠足端位置区分不了

给定足端位置 `p`，`q0` 有两个解：腿朝下、腿翻到水平面以上。自检时随机采样采到上翻位形，误差直接 2.6 rad。

行走时腿恒在身体下方，固定取 `z_leg < 0` 分支即可。**但这个假设必须写进注释**，否则以后调 IK 会怀疑是公式错了。

膝关节同理固定取 `q2 < 0`（与 `go2.xml` 的 knee range 一致）。

## 二、步态与控制

```
vx/vy/wz ─> 步态相位 ─> 足端轨迹 ─> IK ─> q_des ─> PD+前馈 ─> τ ─> 电机
```

trot，duty 0.5，对角腿同相（FL+RR / FR+RL）。

### 转向 = ω × r，不是唯象规则

每条腿的落脚速度不一样，来自刚体速度公式：

```python
v_foot = v_body + ω × r          # r 是该足端相对机体中心的位置
       = [vx - wz*r_y,           # 左右腿步长差动
          vy + wz*hip_x]         # 前后腿反向横扫
```

x 差动和 y 横扫**是同一个公式的两个分量**，不是两套机制。实测贡献：x 差动 +102°，y 横扫 +196° —— **y 横扫才是主力**，跟"转向靠差速"的直觉相反。

### 坑 2：纯 PD 一定会下沉

指令站立高度 0.28，实测只有 0.252。稳态误差 = `τ_重力 / Kp`。

加上 `τ_ff = JᵀF`（支撑腿平分体重）后变成 0.290。这就是「PD + 重力补偿」的实际含义 —— 而且它**复用了第 1 阶段的 Jacobian**，不是两件独立的事。

前馈符号 `F = [0,0,-mg/n]` 是实测定的，翻过来高度掉到 0.206。虚功原理的 `τ = ±JᵀF` 各家约定不一，与其推不如在仿真里试一次。

## 三、实测性能

平地扫参（12s，指令 0.4 m/s）：

| Kp | period=0.25 | 0.35 | 0.5 |
|---|---|---|---|
| 60 | -0.002 | 0.038 | 0.085 |
| 100 | 0.051 | 0.111 | 0.156 |
| 200 | 0.189 | 0.210 | **0.235** |

定为 `Kp=200, period=0.5`。三通道达成率：

| 指令 | 实测 | 达成率 |
|---|---|---|
| `--vx 0.4` | 0.331 | 80% |
| `--wz ±0.8` | ±0.714 / ±0.724 | 89% / 91% |
| `--vy 0.3` | 0.271 | 90% |

缺的 20% 全是足端滑移 —— `step_len = vx × t_stance` 假设支撑腿不打滑。真正的修法是 Raibert 落脚点启发式（用实测速度反馈修正落脚位置），属于第 4 阶段。

## 四、地形

MuJoCo 加载地形三条路，`terrain.py` 三条都用了：

| 方式 | 适合 | 实现 |
|---|---|---|
| box geom 拼装 | 楼梯、障碍块等有棱角的规则几何 | `stairs` `boxes` `slope` |
| **heightfield** | 连续起伏，MuJoCo 原生机制 | `rough` `waves`，也可读 PNG |
| 直接换 XML | 整个场景替换 | `--scene <path>` |

都用 `MjSpec` 在内存里改模型，不生成 XML 文件。**原因**：`go2.xml` 里 `meshdir="assets"` 是相对**主模型文件**目录解析的，把生成的 scene 写到别的目录会导致所有 mesh 找不到。

结果（12s，指令 0.4 m/s）：

| 地形 | vx | |
|---|---|---|
| flat | 0.331 | |
| rough | 0.333 | hfield 起伏 6cm |
| waves | 0.329 | hfield 正弦波纹 |
| slope | 0.285 | 10° 斜坡 |
| boxes | 0.277 | 随机碎石 |
| **stairs** | **0.082** | ❌ 卡在第一级 |

粗糙度扫到 24cm 起伏仍能走（0.317 m/s），几乎不掉速。

### 坑 3：hfield 与 floor 平面重叠

hfield 实体从 `-base`(-5cm) 到 `+z_max`(+6cm)，而原场景的**无限大** floor 平面在 z=0 横穿过去，脚被夹在两个碰撞面之间。

现象：**姿态完美、四脚着地、零位移**。加 hfield 必须先删 floor。

### 坑 4：机器人出生在地形内部

keyframe 里 base 高度 0.27 是按平地写死的（脚刚好触地）。地形一起伏，脚就生成在地面以下，腿卡在网格里。

现象同样是零位移。定位线索是**腿的摆动范围被压缩**（0.81~0.99 rad vs 平地 0.71~1.07）。现在按 hfield 最大高度自动抬升出生点，并加 0.5s 落定阶段。

## 五、楼梯为什么爬不上去 —— 这是重点

抬腿高度 `step_h=0.06` < 台阶高度 `rise=0.08`，脚在摆动最高点仍低于台阶面，直接撞立面。

把腿抬高？

| step_h | 结果 |
|---|---|
| 0.06 | 卡住 |
| 0.12 | 摔倒 @x=0.75 |
| 0.16 | 摔倒 @x=0.10 |

**抬得越高摔得越早** —— 摆动腿惯性反作用越大，而控制器没有任何姿态反馈去抵消。和「Kp=60 时往后走」是同一个病根。

这不是参数没调好，是**结构性缺陷：这个控制器是瞎的**。

```
它知道：  相位、指令速度
它不知道：地面在哪、脚有没有踩实、身体歪没歪
```

24cm 起伏的 rough 能走，8cm 的楼梯走不了。区别在**连续性**：hfield 处处连续，脚盲放下去总能踩到承重面；楼梯有垂直立面。

> **地形难度对盲走控制器不是看高度差，是看有没有不可通过的竖直面。**
> 对 RL 的 terrain curriculum 有直接含义：难度按起伏幅度线性排是不对的，
> 加入 discrete 台阶那一刻难度是**跳变**的。

缺的三样正好对应后续阶段：

| 缺什么 | 阶段 |
|---|---|
| 机身姿态和速度（抵消摆动腿反作用） | 第 3 阶段 状态估计 |
| 脚何时触地（而非按固定相位切换） | 第 3 阶段 接触检测 |
| 按触地时机自适应调整落脚点 | 第 4 阶段 经典 locomotion |

也可以直接跳第 5 阶段用 RL。但现在能更具体地回答「RL 到底替我解决了什么」：
**不是替你算 IK（IK 你已经写出来了，精度 1e-16），而是替你处理「看不见地面时怎么落脚」。**

## 六、最大的教训：先怀疑测量，再怀疑控制

这轮踩的坑里，**有两个是测量 bug，但都表现得像控制 bug**：

**1. yaw 混叠。** 用 `np.unwrap([起始yaw, 结束yaw])` 算转角只能分辨 ±180°，而 `0.8 rad/s × 8s = 367°` 早就超程。读数出来是 -32.8°，**符号都反了**，我据此报了「转向方向错误」并差点去改本来正确的 `ω × r` 符号。改成逐步累积后真值是 +327.2°，控制器从头到尾都是对的。

**2. 世界系位移 ≠ 机体速度。** 一转向，绕圈走回原点，`dx/duration` 测出 `vx≈0`。必须把世界系速度投影回机体系再积分。

**3. 摔倒判据用绝对高度。** `qpos[2] < 0.15` 在楼梯上会误判（爬上去高度本来就涨）。改用机身 z 轴倾角。

> 调 RL 的 reward 或看 sim2real 差异时，**先确认量出来的东西是不是你以为的东西** ——
> 尤其涉及角度和转动的时候。
